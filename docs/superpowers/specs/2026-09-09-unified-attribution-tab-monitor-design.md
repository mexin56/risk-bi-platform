# 授信归因与资金归结统一监控页设计

## 目标

将授信归因监控与资金归结监控放入同一个归因监控页面，通过页面内 Tab 切换。两套监控使用同一套页面骨架、交互和结果存储生命周期；仅替换数据源、字段映射和计算口径。

第一版以授信归因监控页为唯一 UI 基线，不沿用当前资金版的独立卡片布局，不新增与授信页无对应关系的 KPI 或视觉组件。

## 范围与非目标

包含：

- 统一归因页及“授信归因 / 资金归结”两个 Tab。
- 资金版按模板 v1.2 的计算、缓存、预计算快照、路径趋势和规则状态。
- 授信与资金两套结果的字段映射、筛选、路径详情和状态历史。
- 使用给定 XLSX 作为资金结果核验基准。

不包含：

- 不改造资金异常订单底层识别规则。
- 不新增资金流图谱、账户关系图或案件定性功能。
- 不把授信指标强行套到资金版，也不为资金版自由设计另一套页面。
- 不重构授信归因现有计算逻辑。

## 页面结构

入口页面改为统一的归因监控页面，现有授信归因页的内容作为默认 Tab。页面顶部增加唯一的 Tab 切换条：

- `授信归因监控`：继续使用现有授信归因 API、字段、阈值和结果结构。
- `资金归结监控`：使用资金归结 API、资金模板 v1.2 字段和结果结构。

两个 Tab 内部严格复用授信页的结构：

1. 顶部工具栏：观察区间、数据分区、刷新归因、数据表、缓存状态、分享、截图。
2. 合并预警结果卡片：规则状态 Tabs、来源/层级/异常类型/主窗口/等级筛选、飞书风格结果表。
3. 选中路径分析：路径趋势图、当前状态、主窗口摘要、近 1/3/7 天窗口解释卡。
4. 底部双卡片：免归因抑制与审计、预警阈值与运行口径。

资金 Tab 不保留当前 `FundMonitor.tsx` 的独立 KPI 卡、独立结果 Tabs、独立 Recharts 表格或其他自定义布局。资金结果表只将授信字段替换为资金字段：

| 授信页字段 | 资金页字段 |
| --- | --- |
| 授信申请量 | 异常订单量 |
| 通过率（件数/人数） | 异常率 |
| 授信路径 | 资金归结路径 |
| 申请增长 | 异常订单量增长 |
| 结构提升 | 异常订单结构占比提升 |
| 超额量 | 超额异常订单 |

资金趋势图使用异常订单量柱状图与异常率折线图，窗口阴影和基准日均线沿用授信趋势图样式；不添加资金流关系图。

## 页面路由与权限

- 统一页面内部使用 `page=attribution`。
- 分享链接增加 `tab=credit|fund`，保留分区、回看偏移、路径、筛选和趋势范围参数。
- 旧的 `page=fundMonitor` 链接兼容为统一页面的资金 Tab，不再渲染独立页面。
- 统一导航项显示“归因监控”，并在页面内显示两个 Tab。
- Tab 权限仍独立：授信 Tab 要求 `attribution`，资金 Tab 要求 `fundMonitor`；只有资金权限的用户默认进入资金 Tab，只有授信权限的用户默认进入授信 Tab。
- 后端接口权限不合并：授信继续使用 `attribution`，资金继续使用 `fundMonitor`。

## 资金计算口径

资金计算严格实现 DOCX v1.2 与 XLSX 运行结果中的口径：

- 数据表：`pb_biz_credit.lj_cap_flow_analysis_base`。
- 日期字段：`create_date`。
- 异常字段：`payee_last1_cnt_cate`，按 0/1 异常标记聚合。
- 归因维度：`ser_call_node`、`cus_flag`、`cashloan_cid_mob_type`、`loan_cust_lifecycle_stage`、`traffic_channel`、`reg_sx_days`、`sx_order_days`、`register_software`、`state_name_clean`。
- 观察窗口：最新 1 天、3 天、7 天。
- 每个窗口的基准期：该窗口观察期之外的全部历史日期，不截断为固定 15 天。
- 预警门槛：Level1/2/3 必须同时满足观察异常订单数、异常量增长倍数、异常率提升倍数和正向 z-score 四项门槛。
- Top-K 链路：单维全量扫描 → 内部 Top10 → 二级 → 内部 Top5 → 三级终止。
- 专家规则：保留模板中的生命周期强制单维规则；专家规则绕过剪枝但不绕过统一指标和预警门槛。
- 合并：以规范化 `字段=取值` 路径去重，同路径同时命中时来源为“Top-K + 专家规则”，等级取三窗口最高等级。

资金页面显示的“无预警候选”也遵循授信页逻辑：当前发现列表保留 Top-K/专家链路候选中的 Level0 路径，正式预警与候选不混淆。

## 数据存储与服务生命周期

资金版按授信归因的“计算进程写入、API 只读快照”模式实现，但使用独立物理库和目录，避免两种业务路径互相覆盖：

- DuckDB：`server/data/fund_attribution.duckdb`。
- serving 快照：`server/data/fund_serving/`。
- 页面缓存：保留资金独立缓存键和目录。
- 规则状态：`fund_attribution_status.sqlite3`，复用 `AttributionStatusStore` 的表结构、状态值、历史记录和追踪规则逻辑。

资金预计算写入与授信相同的结果分层：运行批次、汇总、预警路径、每路径每窗口指标、日趋势、路径日序列、抑制路径、规则结构和完整 payload。发布阶段使用临时文件写入后原子替换，API 读取完整 Parquet 快照。

资金 API 保留以下语义：

- `partitions`：发现分区和日期范围。
- `dashboard`：优先内存缓存、磁盘缓存和 serving 快照；无缓存时可在线计算兜底。
- `force=true`：有旧结果时立即返回旧快照并后台重算，前端轮询 `generated_at`。
- `path-trend`：从路径日序列快照读取选中路径趋势。
- `rule-status` / `rule-status-history`：与授信页相同的标记、追踪和历史审计语义。

## 组件边界

- `AttributionMonitor.tsx`：统一 Tab 容器、权限判断、旧链接兼容和 Tab 状态。
- `CreditAttribution.tsx`：保留授信计算字段与现有展示行为，必要时只提取共享 UI 片段。
- `FundAttribution.tsx`：严格复用授信页的布局和交互状态，使用资金 API/类型/格式化函数。
- 第一版不抽取 `AttributionMonitorShell`，不重构授信页；统一容器只负责 Tab、权限和旧链接兼容，资金页按授信页同构实现。
- `fund_attribution.py`：资金指标和归因编排，保持与模板口径一致。
- `fund_pipeline/`：资金 DuckDB 持久化、Parquet 发布与只读组装，接口形态对齐现有授信 pipeline。
- `fund_service.py`：资金快照优先、在线兜底、状态覆盖和 API 路由。

## 验证方案

后端：

- 用现有资金合成数据测试窗口切分、全历史基准、Level 门槛、Top-K、专家强制和合并去重。
- 验证 API 的分区、快照、强制刷新、路径趋势、规则状态和鉴权行为。
- 检查资金 serving 快照能够被 API 进程只读加载，旧缓存不会覆盖更新快照。

结果核验：

- 对照 XLSX 的“结论摘要”“窗口总览”“专家_强制单维结果”“大盘日趋势”。
- 资金样本基准值为：60 个有效日期、867724 个总订单、2409 个异常订单；最终正式预警为 0；专家强制单维为 3 条。
- 核对近 1/3/7 天的观察天数、基准天数、基准/观察异常订单、异常率、增长倍数、提升倍数和 z-score。

前端：

- `npm run build`。
- 在统一页面中切换两个 Tab，确认授信 Tab 行为不回归、资金 Tab 页面结构与授信 Tab 对齐。
- 验证分享链接、旧 `page=fundMonitor` 链接、筛选、路径点击、趋势重试、截图和规则状态更新。

## 第一版交付顺序

1. 先完成统一页面 Tab 和授信/资金权限兼容。
2. 将资金 UI 重做为授信页同构结构。
3. 将资金结果接入授信同款 DuckDB/serving 生命周期。
4. 接入样本核验与后端/前端测试。
5. 启动前端，用统一页面实际检查两个 Tab 的视觉和交互效果。
